    API Reference

    Python API#

    The Python API — AUTOMATA's primary user-facing interface — landed in Phase 5 (PyO3 bindings, crate automata-python). Build and install everything with one script:

    python scripts/build.py            # engine + Python wheel + install
python scripts/build.py --all      # also run the gates and test suites
python scripts/build.py --help     # all stages and flags

    Example#

    import automata as at

game = at.Game(title="Demo", resolution=(1280, 720))

game.load_scene(
    at.Scene()
    .add(at.Entity("cube").add(at.Transform(position=(0, 0, 0))))
    .add(at.Entity("camera").add(at.Camera3D(position=(0, 0.5, 4), target=(0, 0, 0))))
)

@game.update
def tick(ctx):
    if ctx.input.just_pressed("escape"):
        ctx.quit()
    cube = ctx.scene["cube"]            # like find(), but raises KeyError
    _, ry, _ = cube.transform.rotation_euler
    cube.transform.rotation_euler = (0, ry + ctx.time.delta, 0)

@game.on_event("hit")
def on_hit(payload):
    print("hit!", payload)              # runs after tick, once per event

game.run()  # uses the @game.update callback; game.run(fn) works too

    Object-oriented style#

    Game, Scene, and Entity are subclassable. Engine options are class attributes; lifecycle hooks are methods; methods named on_<event> are auto-registered as event handlers:

    import automata as at

class Player(at.Entity):
    def __init__(self):
        super().__init__("player")
        self.add(at.Transform(position=(0.0, 1.15, 0.0)))
        self.add(at.RigidBody.kinematic_velocity())
        self.add(at.Collider3D.capsule(0.5, 0.4))
        self.add(at.CharacterController(snap_to_ground=0.5))
        self.add(at.CharacterVelocity())

class Level(at.Scene):
    def __init__(self):
        super().__init__()
        self.add(Player())

class Platformer(at.Game):
    title = "Platformer"
    resolution = (1280, 720)

    def on_start(self):                # once, before the first frame
        self.load_scene(Level())

    def on_update(self, ctx):          # every frame
        player = ctx.scene["player"]
        if ctx.input.just_pressed("escape"):
            ctx.quit()

    def on_hit(self, payload):         # every readable "hit" event
        print("hit!", payload)

Platformer().run()

    The decorator and procedural styles keep working unchanged; constructor keyword arguments override class attributes. See examples/python/oop_platformer.py for a complete game.

    The surface supports OO style (above), procedural style (plain functions passed to game.run(update)), and functional style (`game.run(lambda ctx: ..., max_frames=10)). Builders chain (Scene().add(...).add(...)`), components are mutable (t.position = (1, 2, 0)), and scene views support scene["name"] indexing and iteration (for e in ctx.scene).

    Loading scenes made in Oberon#

    The Oberon editor saves the engine's RON scene-file format (Ctrl+S writes scene.ron, then scene-2.ron, … in the directory Oberon was started from), so its files load directly:

    import automata as at

game = at.Game(title="my level")
game.load_scene(at.Scene.load("scene.ron"))   # IOError / ValueError on failure

def update(ctx):
    player = ctx.scene["Player"]              # entity names from the Hierarchy
    player.character_velocity = (3.0, -2.0, 0.0)

game.run(update)

    Physics, meshes, lights and Character Controllers come across as authored; gameplay (input → movement, cameras) is your Python code. examples/python/play_oberon_scene.py scene.ron reproduces Oberon's Play mode (WASD/arrows, Space, Shift, follow camera) as a starting point.

    Behaviour scripts#

    Attach a script to an entity in Oberon (Inspector → Script → New…). A script is a plain module with optional start(entity, ctx), update(entity, ctx) and stop(entity, ctx) functions:

    # scripts/spinner.py
def start(entity, ctx):
    entity.state["speed"] = entity.attributes.get("speed", 1.5)

def update(entity, ctx):
    rx, ry, rz = entity.transform.rotation_euler
    entity.transform.rotation_euler = (rx, ry + entity.state["speed"] * ctx.time.delta, rz)
    if ctx.input.just_pressed("space"):
        print("boing")                      # → Oberon's Console

    In Oberon's Play mode the scripts run in a separate Python process bridged to the editor (any python3; set python in ~/.config/oberon/prefs.ron to pick one). Saving a script while playing hot-reloads it, and errors show in the Console with a clickable File "…", line N. The same files run in the engine with:

    at.run_scene("level.ron")                  # Game options as keywords

    entity has name, transform, character_velocity, attributes, grounded and a persistent state dict; ctx has input, time, physics, scene, log(...) (plus events, resources, quit() in the engine). Scripted characters skip Oberon's built-in WASD controller.

    Attributes and prefabs#

    Custom attributes added in Oberon's inspector (bool, int, float, text, vector, color) travel with the scene file and read like a dict — on staged entities and live ones alike:

    enemy = ctx.scene["Enemy"]
hp = enemy.attributes.get("health", 100)
enemy.attributes["health"] = hp - 10      # buffered, like transform writes
enemy.script                              # "scripts/enemy.py" if attached

    Values map to bool, int, float, str, (x, y, z) and (r, g, b, a).

    Prefabs (.prefab files saved from Oberon's Hierarchy, or Prefab(entity).save(path) from code) are reusable entity templates:

    crate = at.Prefab.load("prefabs/crate.prefab")
scene.add(crate.instantiate(position=(2, 0, 0), name="crate_1"))   # staged
ctx.scene.spawn(crate, position=(0, 5, 0))                         # at runtime

    Ownership and consistency rules#

    • Game owns the engine. run borrows it for the whole loop; a game that has shut down cannot run again (raises automata.Error).
    • Scene/Entity are plain-data builders; load_scene copies them into the ECS world. After loading, entities are addressed by id or name.
    • FrameContext carries start-of-frame snapshots for reads and a write buffer for changes (transforms, spawns, despawns, events). Buffered writes apply right after the callback returns and are visible from the next frame. Writes through TransformRef attributes compose field-by-field within the frame (tref.position = ...; tref.scale = ... does not clobber), and reads through them see pending same-frame writes. No live engine borrows cross into Python, so a context object that escapes its callback is stale but harmless.
    • Key names are lowercase snake_case ("w", "arrow_left", "f1", "escape", ...); mouse buttons are "left", "right", "middle", "back", "forward".

    Type stubs for editors ship in automata/_core.pyi.

    Canonical usage:

    use automata_core::{Application, EngineConfig, Result, WindowMode};
use automata_input::KeyCode;

fn main() -> Result<()> {
    let config = EngineConfig {
        // Headless runs without a window/GPU: tests, CI, tooling.
        window_mode: WindowMode::default(),
        ..EngineConfig::new("My Game")
    };
    let mut app = Application::new(config);
    app.run(|ctx| {
        // one call per frame
        if ctx.input().just_pressed(KeyCode::Escape) {
            ctx.request_quit();
        }
    })
}

    Phase 6 — Physics and Input#

    Physics model#

    • Attach a RigidBody plus a Collider3D (3D) or Collider2D (2D) to an entity to make it physical. The engine syncs the physics world from the scene, steps it at a fixed timestep (EngineConfig::physics_timestep, default 1/60 s), and writes resulting transforms back.
    • Entities with a 2D collider live in the 2D world; those with a 3D collider (or none) live in the 3D world. A single scene can mix both.
    • Collision events (PhysicsEvent::{CollisionStarted, CollisionStopped}) and contact-force events arrive on the event bus.
    • Kinematic character controllers (CharacterController + CharacterVelocity) move with slide/slope/autostep/snap-to-ground logic; ctx.physics.grounded(entity) reports ground contact. Drive a character per frame with view.character_velocity = (vx, vy, vz) (buffered like transform writes); game code composes gravity/jumps into the velocity.
    • Scripts never see Rapier: the engine owns the simulation and exposes queries/mutations through the frame context only.

    Input model#

    • Keyboard/mouse state: ctx.input.pressed(key) / just_pressed / just_released, plus mouse buttons, cursor, scroll, modifiers.
    • Gamepads (gilrs): ctx.input.gamepads — connected pads by id (ids, get, primary), button/axis state (pressed, pressed_any, axis, axis_any), sticks (pad.left_stick()), and this frame's connection/button/axis events (gamepads.events).
    • Action mapping: automata.ActionMap binds named actions and axes to any device (Binding.key / mouse / gamepad_button / axis thresholds, AxisBinding.gamepad_axis / key_pair / button_pair), evaluates against ctx.input, and is remappable at runtime (bind, rebind, unbind). Game code never touches raw device ids.
