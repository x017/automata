    Development Guide

    Prerequisites#

    • Rust stable (MSRV: 1.86), with rustfmt and clippy
    • Python 3 (from Phase 5 onward)

    Standard setup via rustup:

    rustup component add rustfmt clippy

    Offline / sandboxed environments#

    Some development sandboxes cannot reach static.rust-lang.org or crates.io. For those, the repository provides a bootstrap path that ferries a toolchain and vendored dependencies through GitHub Actions artifacts:

    1. Run the bootstrap-toolchain workflow (.github/workflows/bootstrap-toolchain.yml). It packages the stable toolchain (with rustfmt and clippy) and the cargo vendor output as workflow artifacts.

    2. From the sandbox, fetch and install them:

      ./scripts/setup-offline-env.sh
export PATH="$HOME/.local/automata-rust/stable-x86_64-unknown-linux-gnu/bin:$PATH"

      The script also writes .cargo/config.toml (git-ignored) pointing Cargo at vendor/, so builds work fully offline.

      Note for sandboxed sessions: only git-tracked file contents persist across sandbox sessions — the toolchain (~/.local/automata-rust), vendor/, and .cargo/config.toml are wiped between sessions. Re-run scripts/setup-offline-env.sh at the start of every session.

    1. Re-run the bootstrap workflow whenever dependencies change (it triggers automatically on changes to any Cargo.toml).

    Everyday commands#

    cargo run -p automata-core        # run the engine entry point
cargo test --workspace            # unit + integration + doc tests
cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --all -- --check
cargo doc --workspace --no-deps --open

    All of the above run in CI and must stay green.

    Python bindings#

    The automata-python crate builds the automata Python package with maturin:

    python3 -m venv .venv
.venv/bin/pip install maturin pytest
.venv/bin/maturin build --manifest-path crates/automata-python/Cargo.toml
.venv/bin/pip install target/wheels/automata_engine-*.whl
.venv/bin/python -m pytest crates/automata-python/tests/python
.venv/bin/python examples/python/headless_demo.py

    Sandbox note: the sandbox has no libpython, so linking any target that embeds Python fails locally. Workarounds baked into the workflow:

    • Build/clippy the bindings with PYO3_BUILD_EXTENSION_MODULE=1 (this is what maturin sets; it skips the libpython link).
    • Run cargo test --workspace --exclude automata-python locally; the crate's Rust unit tests link libpython and therefore run on CI only.
    • Python-side behavior is covered locally by the pytest suite against the maturin-built wheel, which links without libpython by design.

    Documentation site#

    The wiki and engine docs are also published as static HTML under docs/site/docs/, generated from the Markdown by scripts/build_site.py (standard library only). The Markdown is the source of truth: after editing any page under docs/wiki/ or docs/*.md, rebuild and commit the output.

    python3 scripts/build_site.py           # regenerate docs/site/docs/
python3 scripts/build_site.py --check   # what CI runs: fails if stale
python3 -m http.server -d docs 8000     # preview at http://localhost:8000/site/

    New pages must be added to NAV in the script to get a sidebar entry. The page styles and scripts live in scripts/site/ and are copied into docs/site/docs/_static/.

    Landing page (docs/site/index.html + docs/site/landing.js). It is set in Bricolage Grotesque, with JetBrains Mono for code. Both are OFL and vendored in docs/site/fonts/. landing.js is a tiny hidden-line 3D renderer on a 2D canvas, styled after Oberon's scene view. It draws the hero scene and the coin.py playground, whose yellow numbers are draggable sliders running the same logic as the tutorial script. It also drives the Oberon tour, which highlights regions of the screenshots in docs/assets/oberon/. If you regenerate those screenshots with a different layout, update the data-rect values (in 1600×950 pixels) in index.html.

    Docs pages use editorial type (Geist with Instrument Serif for display) and one-bit dithered art. docs/site/dither.js provides the dither-to-colour "develop" effect on screenshots. The section banners in docs/site/img/ are exported from the same shader with scripts/site/export-art.html; its header lists the parameters for each.

    Everything honours prefers-reduced-motion, and the pages work without JavaScript (the canvases simply stay empty).

    Coding conventions#

    • Edition 2021, MSRV 1.86 (bumped deliberately, not casually).
    • No unsafe in engine crates — enforced workspace-wide.
    • Document every public item. missing_docs is a workspace lint and CI denies warnings. Document why, not just what.
    • Errors: libraries define a crate-local Error enum with thiserror plus a Result<T> alias. Recoverable conditions are Results, never panics. Panics signal programmer error only.
    • Logging: use tracing macros (info!, debug!, …). Library code never prints to stdout/stderr directly.
    • Dependencies: prefer mature, maintained crates (build.md section 2). Declare shared dependencies in the workspace root [workspace.dependencies] and inherit with dep.workspace = true. New dependencies require a stated reason in their commit message.
    • Formatting: rustfmt.toml holds the canonical style. Lint policy lives in the workspace [workspace.lints] tables — exceptions are documented there, not scattered across the code.
    • Tests: unit tests next to the code, integration tests in tests/, doc tests for public API examples. New functionality ships with tests (build.md section 10).

    Working agreements (AI-assisted development)#

    Per build.md section 10:

    • Implement one subsystem at a time; keep the build green after each step.
    • Inspect existing code before modifying it; no large uncontrolled rewrites.
    • Verify dependency APIs against official documentation.
    • Every completed subsystem has a defined public interface and tests.

    Commits and branches#

    • Imperative commit messages (Add …, Fix …), referencing the phase or subsystem where relevant (phase 1: …).
    • main must always build. Feature work happens on branches and lands via pull request with green CI.
