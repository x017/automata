    Guide: Performance

    How many scripted entities fit in a frame? This page answers that with measured numbers, explains what the numbers include, and shows how to measure on your own machine.

    Practical limits#

    At 60 FPS a frame lasts 16.7 ms, and that time is shared by your scripts, physics and drawing. On the reference machine below:

    • Plain scripted entities cost about 15 µs each per frame in a game (run_scene or an exported build). About 1,000 fit in a 60 FPS frame before anything is drawn. Keep to around 700 to leave room for rendering.
    • Scripted physics characters (a character controller each) cost about 50 µs each. Keep to around 250.
    • Oberon Play takes 1.5 to 2 times as long per frame as the game, because every frame crosses to a separate Python process and back. A scene that runs at 30 FPS in Play can run at 60 FPS once exported. Judge final performance with run_scene or an export, not in the editor.

    Script time grows in proportion to the number of scripted entities, so you can scale these figures to your own scene. A faster CPU than the reference machine (a small cloud VM) will fit more.

    What is measured#

    The scenes come from examples/bench/build_scenes.py. Every entity runs the same script, examples/bench/bench.py. Each frame it reads two attributes, moves its entity in a small circle and casts a ray down at the ground, which is what most gameplay scripts do.

    • scripts scenes: cubes that move by writing their transform.
    • physics scenes: capsules with a character controller, moved through entity.character_velocity, so physics work grows with the entity count too.

    The columns:

    • Avg frame / p95 frame: the average frame, and the frame that 95% of frames beat. The p95 figure shows how bad the occasional slow frame gets.
    • Script: time spent running every entity's update.
    • Engine: everything else in the frame. That covers the physics step, character controllers, syncing the world, and in Oberon Play the trip to the script process and back.
    • FPS: 1000 divided by the average frame time.

    The runs are headless, so drawing isn't included. Rendering cost depends on your GPU, resolution and graphics quality rather than on the script count. Leave part of the frame for it.

    Every runner advances the game by exactly 1/60 s per frame (the fixed_delta option of at.Game). Physics therefore takes one step per frame however long the frame took, and each row shows the cost of one 60 Hz frame. A real game that falls below 60 FPS runs extra physics steps to catch up, up to four per frame, so it slows down faster than these rows suggest.

    Measure on your machine#

    python examples/bench/run.py            # every scene in every runner
python examples/bench/run.py --quick    # 100 and 1,000 entities only
python examples/bench/run.py --runners run_scene --sizes 100,1000,5000

    Run it with the Python that has automata installed. It builds the release binaries with cargo (oberon, automata-cli and automata-player), writes the scenes to examples/bench/scenes/, runs each one and prints the table above with your machine and the date. --out results.json also saves every frame time. A run that exceeds --seconds (default 30) of measuring stops early and reports the frames it managed.

    For the export runner it uses an installed export template if there is one, otherwise a development template made from the freshly built player.

    The runners can also be used on their own:

    • Oberon Play: oberon --bench scene.ron --frames 300 --out stats.json runs a scene the way Play mode does, without a window.
    • run_scene and exported games: set AUTOMATA_FRAME_STATS=stats.json and the run writes every frame's time and script time when it ends. AUTOMATA_FRAME_STATS_WARMUP sets the frames to skip (default 30). An exported game takes --headless --frames N --fixed-delta 0.0166667.

    Rendering a big world#

    run.py measures scripts and physics, not drawing. The renderer has its own benchmark: a forest of 10,000 copies of examples/models/tree.glb with a sun casting shadows, fog, and a camera standing among the trees.

    python examples/bench/forest.py                       # 10,000 trees, High, 1280x720
python examples/bench/forest.py --draw-distance 80    # trees vanish past 80 m
python examples/bench/forest.py --trees 2000 --quality ultra --frames 30

    It renders with Oberon's render_still example and prints the median frame time, including the time to read the image back. Measured in software rendering (lavapipe, 2026-11, 5 frames, High):

    Rendererms/frameSpeed-up
    Before A11 (one draw per mesh part, no culling outside shadows)9,4931×
    Culling + instancing + batching1,0988.6×
    Same, with draw_distance=80 on the trees72313×

    The first two produce identical images. With the draw distance, 110 pixels out of 921,600 differ, because the fog already hides trees that far away. On a real GPU every number is far lower. Compare runs on the same machine.

    The renderer does three things for big worlds:

    • Culling. Meshes outside the camera's view aren't drawn. Each shadow cascade only draws the meshes that can throw a shadow into it.
    • Instancing and batching. Every copy of the same mesh with the same material, from the same model file or built the same way, is drawn in a single call. Materials with equal colors, surfaces and textures count as the same. Shadow passes group by mesh alone. Skinned (animated) meshes are still drawn one by one.
    • Levels of detail and draw distance. Far copies switch to the model's _LOD1, _LOD2… versions, and meshes past their draw distance aren't drawn at all, shadow included. See Models.

    What helps your scenes most: reuse the same model files and materials instead of building near-identical copies, and give scattered props a draw distance that ends inside the fog.

    Rerun the benchmark before each release and update this page, so that a slowdown shows up as a change in the table.
